# DAHAB — FRONTEND-FIRST WORLD-CLASS PRODUCT TRANSFORMATION
# MASTER CLAUDE CODE DIRECTIVE
#
# Mission:
# Transform the existing Dahab MVP into a highly polished, differentiated,
# production-grade destination platform.
#
# PRIMARY EMPHASIS:
# 1. Deep understanding of the existing frontend
# 2. Radical improvement of UX
# 3. High-quality, distinctive UI
# 4. Strong use of 21st.dev MCP
# 5. Strong use of UI UX Pro Max
# 6. Every frontend capability must be backed by real backend/data behavior
# 7. Every feature must be tested after implementation
#
# DO NOT treat this as "add features to an MVP".
# Treat it as a PRODUCT TRANSFORMATION.

============================================================
0. ROLE
============================================================

Act as one integrated senior product team:

- Principal Product Architect
- Principal UX Designer
- Senior UI Designer
- Design Systems Architect
- Staff Frontend Engineer
- Staff Backend Engineer
- Database Architect
- Search Engineer
- AI Product Architect
- Booking/Commerce Architect
- QA Automation Lead
- Accessibility Engineer
- Performance Engineer
- Security Engineer
- Product Analytics Engineer

However:

THE FRONTEND + UX/UI IS THE PRIMARY FOCUS.

The frontend is where the transformation should be most visible.

But no frontend capability may become a disconnected visual prototype.

Every meaningful frontend feature must connect to:

UI
→ UX FLOW
→ STATE
→ API
→ BACKEND
→ DATABASE
→ BUSINESS LOGIC
→ PERMISSIONS
→ ANALYTICS
→ LOGGING
→ TESTS

============================================================
1. NON-NEGOTIABLE RULE — UNDERSTAND BEFORE BUILDING
============================================================

DO NOT immediately start redesigning the UI.

DO NOT immediately rewrite components.

DO NOT immediately install random components.

DO NOT immediately replace the architecture.

First understand the product deeply.

Phase 0 must be:

AUDIT
→ EXPLORE
→ RESEARCH
→ UNDERSTAND
→ MAP
→ DESIGN
→ PLAN

Only after this phase is complete should implementation begin.

============================================================
4. CRITICAL UI PRINCIPLE
============================================================

THE UI MUST NOT LOOK LIKE AI-GENERATED TEMPLATE UI.

Absolutely avoid:

- generic SaaS aesthetics
- generic startup landing pages
- random gradients
- excessive glassmorphism
- meaningless cards
- repetitive rounded rectangles
- generic Tailwind aesthetics
- "Dribbble-only" design
- visual complexity without usability
- copying Airbnb
- copying Booking
- copying Tripadvisor
- copying Google Travel
- copying another existing product

The goal is NOT:

"make it prettier."

The goal is:

"make the product significantly easier, faster, clearer and more enjoyable to use."

============================================================
5. UI UX PRO MAX — MANDATORY
============================================================

If UI UX Pro Max is available in the project/environment:

USE IT.

Do not ignore it.

Before implementing major UI changes:

- invoke the relevant design intelligence
- analyze the product context
- generate a coherent design direction
- define design tokens
- define component patterns
- define UX patterns
- evaluate alternatives
- apply the system consistently

Do not use UI UX Pro Max as a button that outputs random aesthetics.

Use it as a DESIGN INTELLIGENCE SYSTEM.

For every major screen:

1. Understand its user goal.
2. Understand the information hierarchy.
3. Determine the interaction model.
4. Determine the visual hierarchy.
5. Determine the appropriate interaction patterns.
6. Generate/refine the design direction.
7. Implement only after the design decision is coherent.

============================================================
6. 21ST.DEV MCP — MANDATORY FOR UI WORK
============================================================

Use the 21st.dev MCP when it can materially improve the UI.

Do NOT invent every component from scratch.

Before building substantial UI sections:

1. Search the 21st catalog.
2. Find relevant production-quality patterns.
3. Review available variants.
4. Inspect their implementation.
5. Evaluate dependencies.
6. Compare multiple options when appropriate.
7. Select the best foundation.
8. Adapt it to Dahab's design system.
9. Integrate it into the existing architecture.
10. Verify accessibility, responsiveness and consistency.

Use 21st MCP particularly for:

- navigation
- search interfaces
- filters
- cards
- calendars
- maps UI
- dialogs
- drawers
- sheets
- forms
- onboarding
- dashboards
- data visualization
- booking interfaces
- profile interfaces
- mobile patterns
- interactive sections
- advanced visual components

IMPORTANT:

21st is a source of REAL UI building blocks.

It is NOT permission to create a Frankenstein interface.

Do not combine components with incompatible visual languages.

Every imported component must be adapted to the Dahab design system.

21st documentation indicates the MCP can search the catalog, inspect real code and dependencies, install components, explore design directions, and review UI. Use those capabilities intentionally.

→ database

→ validation
→ tests

# Web Interface Guidelines

Review these files for compliance: $ARGUMENTS

Read files, check against rules below. Output concise but comprehensive—sacrifice grammar for brevity. High signal-to-noise.

## Rules

### Accessibility

- Icon-only buttons need `aria-label`
- Form controls need `<label>` or `aria-label`
- Interactive elements need keyboard handlers (`onKeyDown`/`onKeyUp`)
- `<button>` for actions, `<a>`/`<Link>` for navigation (not `<div onClick>`)
- Images need `alt` (or `alt=""` if decorative)
- Decorative icons need `aria-hidden="true"`
- Async updates (toasts, validation) need `aria-live="polite"`
- Use semantic HTML (`<button>`, `<a>`, `<label>`, `<table>`) before ARIA
- Headings hierarchical `<h1>`–`<h6>`; include skip link for main content
- `scroll-margin-top` on heading anchors
- Meaningful media needs captions, transcripts, or descriptions as applicable
- Media controls need keyboard support; decorative media needs assistive-tech hiding

### Focus States

- Interactive elements need visible focus: `focus-visible:ring-*` or equivalent
- Never `outline-none` / `outline: none` without focus replacement
- Use `:focus-visible` over `:focus` (avoid focus ring on click)
- Group focus with `:focus-within` for compound controls
- Sticky headers/footers/overlays must not cover the focused element

### Forms

- Inputs need `autocomplete` and meaningful `name`
- Use correct `type` (`email`, `tel`, `url`, `number`) and `inputmode`
- Never block paste (`onPaste` + `preventDefault`)
- Labels clickable (`htmlFor` or wrapping control)
- Disable spellcheck on emails, codes, usernames (`spellCheck={false}`)
- Checkboxes/radios: label + control share single hit target (no dead zones)
- Submit button stays enabled until request starts; spinner during request
- Errors inline next to fields; focus first error on submit
- Placeholders end with `…` and show example pattern
- `autocomplete="off"` on non-auth fields to avoid password manager triggers
- Warn before navigation with unsaved changes (`beforeunload` or router guard)

### Animation

- Honor `prefers-reduced-motion` (provide reduced variant or disable)
- Animate `transform`/`opacity` only (compositor-friendly)
- Never `transition: all`—list properties explicitly
- Set correct `transform-origin`
- SVG: transforms on `<g>` wrapper with `transform-box: fill-box; transform-origin: center`
- Animations interruptible—respond to user input mid-animation
- Autoplay motion >5 seconds alongside other content needs pause, stop, or hide controls
- Muted decorative loops must stop under `prefers-reduced-motion`

### Typography

- `…` not `...`
- Curly quotes `“` `”` not straight `"`
- Non-breaking spaces: `10&nbsp;MB`, `⌘&nbsp;K`, brand names
- Loading states end with `…`: `"Loading…"`, `"Saving…"`
- `font-variant-numeric: tabular-nums` for number columns/comparisons
- Use `text-wrap: balance` or `text-pretty` on headings (prevents widows)

### Content Handling

- Text containers handle long content: `truncate`, `line-clamp-*`, or `break-words`
- Flex children need `min-w-0` to allow text truncation
- Handle empty states—don't render broken UI for empty strings/arrays
- User-generated content: anticipate short, average, and very long inputs

### Images

- `<img>` needs explicit `width` and `height` (prevents CLS)
- Below-fold images: `loading="lazy"`
- Above-fold critical images: `priority` or `fetchpriority="high"`

### Performance

- Large lists (>50 items): virtualize (`virtua`, `content-visibility: auto`)
- No layout reads in render (`getBoundingClientRect`, `offsetHeight`, `offsetWidth`, `scrollTop`)
- Batch DOM reads/writes; avoid interleaving
- Prefer uncontrolled inputs; controlled inputs must be cheap per keystroke
- Add `<link rel="preconnect">` for CDN/asset domains
- Critical fonts: `<link rel="preload" as="font">` with `font-display: swap`
- Prefer `<video autoplay muted loop playsinline>` over animated GIF; provide a still alternative
- Short non-essential loops: Safari H.264 MP4 `<picture>` source, `prefers-reduced-motion` media condition, and still fallback

### Navigation & State

- URL reflects state—filters, tabs, pagination, expanded panels in query params
- Links use `<a>`/`<Link>` (Cmd/Ctrl+click, middle-click support)
- Deep-link all stateful UI (if uses `useState`, consider URL sync via nuqs or similar)
- Destructive actions need confirmation modal or undo window—never immediate

### Touch & Interaction

- `touch-action: manipulation` (prevents double-tap zoom delay)
- `-webkit-tap-highlight-color` set intentionally
- `overscroll-behavior: contain` in modals/drawers/sheets
- During drag: disable text selection, `inert` on dragged elements
- Drag/swipe/pinch/path gestures need tap/click and keyboard alternatives unless essential
- `autoFocus` sparingly—desktop only, single primary input; avoid on mobile

### Safe Areas & Layout

- Full-bleed layouts need `env(safe-area-inset-*)` for notches
- Avoid unwanted scrollbars: `overflow-x-hidden` on containers, fix content overflow
- Flex/grid over JS measurement for layout

### Dark Mode & Theming

- `color-scheme: dark` on `<html>` for dark themes (fixes scrollbar, inputs)
- `<meta name="theme-color">` matches page background
- Native `<select>`: explicit `background-color` and `color` (Windows dark mode)

### Locale & i18n

- Dates/times: use `Intl.DateTimeFormat` not hardcoded formats
- Numbers/currency: use `Intl.NumberFormat` not hardcoded formats
- Detect language via `Accept-Language` / `navigator.languages`, not IP
- Brand names, code tokens, identifiers: wrap with `translate="no"` to prevent garbled auto-translation

### Hydration Safety

- Inputs with `value` need `onChange` (or use `defaultValue` for uncontrolled)
- Date/time rendering: guard against hydration mismatch (server vs client)

# Phase 0 frontend audit

## Executive verdict

The frontend is **structurally viable and should not be rewritten wholesale**. Routing/deep-link utilities, route-level splitting, API resource handling, bilingual document setup, and several server-backed commerce journeys are solid foundations.

   128	1. **Hold Request (`POST /api/commerce/hold`)**:

   133	   * Increments `heldCapacity` inside a transaction block.
   134	2. **Multi-Checkout (`POST /api/commerce/checkout/multi`)**:
   135	   * Validates hold tokens and active expiration times.
   136	   * Executes atomic database transaction:
   137	     - Converts `HoldEntity` from `ACTIVE` to `CONVERTED`.
   138	     - Decrements `heldCapacity` and increments `reservedCapacity`.
